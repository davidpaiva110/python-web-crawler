# Prompt for GitHub Copilot (Chat / Agent mode)

Build a Python command-line web crawler with the following requirements.

## Functional requirements
- Accepts a base URL as a command-line argument and crawls the site starting
  from it.
- For each page it visits, print the page's URL followed by every URL found
  on that page (all `<a href>` links).
- Only follow links on the **exact same hostname** as the base URL. Do not
  crawl other domains, and do not crawl subdomains either (e.g. if the base
  URL is `example.com`, do not crawl `blog.example.com`). Links to other
  domains/subdomains should still be printed as links found on a page — they
  just shouldn't be fetched/followed.
- Deduplicate pages: a page linked from multiple other pages must only be
  fetched once.
- Handle relative URLs, fragments (`#section`), trailing slashes, and
  case differences in scheme/host as equivalent — don't refetch the "same"
  page because of superficial URL formatting differences.
- Skip non-crawlable link schemes (`mailto:`, `tel:`, `javascript:`).
- Only parse links out of actual HTML responses (check `Content-Type`) —
  don't try to parse images/PDFs/etc. as HTML.
- Handle errors gracefully: timeouts, connection errors, 4xx/5xx responses,
  and malformed HTML must not crash the crawl — report them per-page and
  continue.
- Guard against simple crawler traps (e.g. an infinite chain of distinct
  URLs generated by pagination or session params) using the existing
  in-memory visited-set and the configurable max-pages limit — this is
  enough for a single-run CLI tool; don't add a dedicated trap-detection
  subsystem for this exercise.

## Tooling & architecture
- Use **Poetry** for dependency management, installation, and running the
  code (`pyproject.toml` managed by Poetry, `poetry install`,
  `poetry run webcrawler ...`, `poetry run pytest`, etc.) rather than
  plain `pip`/`venv`.
- Apply **SOLID** and **hexagonal (ports & adapters) architecture**
  principles, even though this is a small CLI app — keep the core crawling
  logic (the domain: URL policy, crawl orchestration) decoupled from
  external concerns (the HTTP client, HTML parser, robots.txt fetching,
  CLI/stdout) via clear interfaces/ports, so an adapter (e.g. the HTTP
  client or the output format) could be swapped without touching the core
  logic. Don't over-engineer this into unnecessary layers for a project
  this size, but the boundaries and dependency direction should be clean
  and explained in the README.

## Non-functional requirements
- **Do not use Scrapy or Playwright.** You may use libraries for HTTP
  requests and HTML parsing.
- Optimize for crawl speed without sacrificing accuracy — use concurrent/
  async I/O (this is an I/O-bound problem: most time is spent waiting on
  network responses, so the design should overlap many in-flight requests
  rather than fetching one page at a time). Use asyncio + an async HTTP client.
- Respect `robots.txt` by default, with a flag to disable that. This idea
  comes from the research articles above (both the ByteByteGo and
  HelloInterview system-design breakdowns call out `robots.txt`/politeness
  as a core crawler concern) — implement it as a small adapter behind its
  own port so it stays decoupled from the core crawl orchestration.
- Support configuring: max concurrency, request timeout, max pages to
  crawl, and a per-request delay for politeness.
- Stream output as pages complete rather than buffering everything until
  the crawl finishes.

## Code quality / structure
- Set this up as a real, installable Python package (`pyproject.toml`,
  console-script entry point), not a single script.
- Separate the pure URL logic (normalization, domain matching, link
  extraction) from the async crawling engine and from the CLI/argument
  parsing, so each can be tested independently.
- Add type hints throughout and configure `mypy`.
- Configure `ruff` (or `flake8`/`black`) for linting/formatting and make
  sure the code passes cleanly.
- Write a test suite with `pytest`:
  - Unit tests for URL normalization, domain-matching (including the
    subdomain-exclusion rule), and link extraction — using handwritten
    HTML fixtures, no network needed.
  - Integration tests for the crawl engine against a **mocked** HTTP
    layer (e.g. `respx` for `httpx`, or `responses`/`aioresponses` for
    whichever HTTP client you choose) — cover same-domain restriction,
    deduplication, error handling, `robots.txt` behavior, and the
    max-pages limit. Don't hit the real network in tests.
  - CLI argument parsing and output formatting tests.
- Actually run the tests, linter, and type checker, and fix anything they
  flag before considering the task done.
- If practical in your environment, do a smoke-test run of the CLI against
  a live small site to confirm the end-to-end wiring works, not just the
  unit tests.
